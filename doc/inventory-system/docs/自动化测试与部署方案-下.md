## 7. CI/CD 持续集成与持续部署

### 7.1 什么是 CI/CD

```
CI（持续集成）= 每次代码提交自动运行构建和测试
CD（持续部署）= 测试通过后自动部署到服务器

传统方式（手动）：
  写代码 → 手动测试 → 打包 → 手动上传服务器 → 手动重启
  问题：耗时、易出错、容易忘记步骤

自动化方式（CI/CD）：
  写代码 → git push → 机器人自动完成所有后续步骤
  好处：快速、一致、可追溯
```

### 7.2 工具选型：GitHub Actions

与GitHub仓库深度集成、免费额度充足（2000分钟/月）、配置简单。

> 如果代码托管在其他平台，也可以用 GitLab CI、Jenkins 等，原理一样。

### 7.3 CI 流水线配置

```yaml
# .github/workflows/ci.yml
name: CI Pipeline

on:
  push:
    branches: ['*']
  pull_request:
    branches: [main, develop]

jobs:
  # ═══════════ 阶段1：后端检查与测试 ═══════════
  backend-test:
    name: 后端测试
    runs-on: ubuntu-latest
    services:
      mysql:
        image: mysql:8.0
        env:
          MYSQL_ROOT_PASSWORD: test123
          MYSQL_DATABASE: inventory_test
        ports: ['3306:3306']
        options: >-
          --health-cmd="mysqladmin ping"
          --health-interval=10s
          --health-timeout=5s
          --health-retries=3
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: '1.21' }

      - name: 下载依赖
        working-directory: ./backend
        run: go mod download

      - name: 代码格式检查
        working-directory: ./backend
        run: |
          diff=$(gofmt -d .)
          if [ -n "$diff" ]; then echo "$diff"; exit 1; fi

      - name: 静态代码分析
        uses: golangci/golangci-lint-action@v4
        with: { working-directory: ./backend }

      - name: 运行单元测试
        working-directory: ./backend
        run: go test ./internal/... -v -coverprofile=coverage.out

      - name: 运行集成测试
        working-directory: ./backend
        env:
          DB_HOST: localhost
          DB_PORT: 3306
          DB_NAME: inventory_test
          DB_USER: root
          DB_PASSWORD: test123
        run: go test ./tests/integration/... -tags=integration -v

      - name: 上传覆盖率报告
        uses: codecov/codecov-action@v4
        with: { file: ./backend/coverage.out }

      - name: 构建检查
        working-directory: ./backend
        run: go build -o /dev/null ./...

  # ═══════════ 阶段2：前端检查与测试 ═══════════
  frontend-test:
    name: 前端测试
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
          cache-dependency-path: frontend/package-lock.json

      - name: 安装依赖
        working-directory: ./frontend
        run: npm ci

      - name: TypeScript类型检查
        working-directory: ./frontend
        run: npx tsc --noEmit

      - name: ESLint代码规范检查
        working-directory: ./frontend
        run: npm run lint

      - name: 运行单元/组件测试
        working-directory: ./frontend
        run: npm test -- --coverage --watchAll=false

      - name: 构建检查
        working-directory: ./frontend
        run: npm run build

  # ═══════════ 阶段3：E2E测试（前两阶段通过后） ═══════════
  e2e-test:
    name: E2E测试
    runs-on: ubuntu-latest
    needs: [backend-test, frontend-test]
    services:
      mysql:
        image: mysql:8.0
        env: { MYSQL_ROOT_PASSWORD: test123, MYSQL_DATABASE: inventory_test }
        ports: ['3306:3306']
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-go@v5
        with: { go-version: '1.21' }
      - uses: actions/setup-node@v4
        with: { node-version: '20' }

      - name: 初始化测试数据库
        run: mysql -h 127.0.0.1 -u root -ptest123 inventory_test < scripts/init.sql

      - name: 启动后端
        working-directory: ./backend
        run: go run main.go &
      - name: 启动前端
        working-directory: ./frontend
        run: npm ci && npm run build && npm start &
      - run: sleep 10

      - name: 安装 Playwright
        run: npx playwright install --with-deps chromium

      - name: 运行E2E测试
        working-directory: ./e2e
        run: npx playwright test --project=chromium

      - name: 上传测试报告（失败时）
        if: failure()
        uses: actions/upload-artifact@v4
        with: { name: playwright-report, path: e2e/playwright-report/ }

  # ═══════════ 阶段4：安全扫描 ═══════════
  security-scan:
    name: 安全扫描
    runs-on: ubuntu-latest
    needs: [backend-test, frontend-test]
    steps:
      - uses: actions/checkout@v4
      - name: Go依赖漏洞扫描
        uses: golang/govulncheck-action@v1
        with: { work-dir: ./backend }
      - name: npm依赖漏洞扫描
        working-directory: ./frontend
        run: npm audit --audit-level=high
```

│                  ▼                             │

### 7.5 CI 门禁规则

**门禁**就是"不达标不允许通过"的关卡：

| 门禁项 | 规则 | 不通过后果 |
|--------|------|-----------|
| 单元测试 | 全部通过 | ❌ 不能合并PR |
| 集成测试 | 全部通过 | ❌ 不能合并PR |
| E2E冒烟测试 | 全部通过 | ❌ 不能合并PR |
| 测试覆盖率 | ≥ 80% | ⚠️ 警告 |
| 代码规范 | 无lint错误 | ❌ 不能合并PR |
| 安全扫描 | 无高危漏洞 | ❌ 不能合并PR |
| Code Review | ≥ 1人审批 | ❌ 不能合并PR |

GitHub 配置路径：Settings → Branch protection rules → main / develop

```
  ✅ Require a pull request before merging
  ✅ Require approvals: 1
  ✅ Require status checks to pass
     - backend-test ✅
     - frontend-test ✅
     - e2e-test ✅
     - security-scan ✅
  ✅ Require branches to be up to date
```

## 8. Git 分支策略与代码审查

### 8.1 分支模型

```
main（主分支）← 只有经过完整测试的代码，每次合并 = 一次发布
  │
  ├── develop（开发分支）← 日常开发集成
  │     ├── feature/add-inventory-export     ← 功能分支
  │     ├── feature/user-role-management     ← 功能分支
  │     └── bugfix/fix-pagination-error      ← 修复分支
  │
  └── hotfix/fix-login-crash   ← 紧急修复（直接合并到main和develop）
```

### 8.2 开发流程（一个功能从开发到上线）

```
Step 1: 创建功能分支
  git checkout develop && git checkout -b feature/add-export

Step 2: 开发 + 写测试
  编写功能代码 + 对应测试 → 本地测试通过

Step 3: 推送代码，创建PR
  git push origin feature/add-export → GitHub创建PR→develop

Step 4: CI自动运行
  后端测试✅ → 前端测试✅ → E2E测试✅ → 安全扫描✅

Step 5: Code Review
  团队成员审查 → 修改意见/批准

Step 6: 合并到develop → 自动部署测试环境

Step 7: QA验收 → 创建Release PR: develop→main → 审批 → 合并 → 自动部署生产
```

### 8.3 Code Review 检查清单

```
□ 功能正确性：代码是否实现了需求？
□ 测试覆盖：新代码是否有对应测试？
□ 安全性：有没有SQL注入、XSS、权限绕过？
□ 性能：有没有N+1查询、大数据量未分页？
□ 错误处理：异常是否处理了？错误信息是否友好？
□ 代码规范：命名清晰？符合项目规范？
□ 数据库：是否有新索引需求？迁移脚本是否完整？
□ 向后兼容：改动是否影响现有功能？
```

## 9. 自动化部署流程

### 9.1 部署环境规划

| 环境 | 用途 | 触发条件 | URL |
|------|------|---------|-----|
| **开发环境** | 日常调试 | 本地运行 | localhost |
| **测试环境** | 集成测试、验收 | 合并到 develop | staging.example.com |
| **生产环境** | 真实用户使用 | 合并到 main + 审批 | www.example.com |

### 9.2 CD 部署流水线

```yaml
# .github/workflows/deploy.yml
name: Deploy Pipeline

on:
  push:
    branches: [main, develop]

jobs:
  # ═══════════ 部署到测试环境 ═══════════
  deploy-staging:
    name: 部署测试环境
    if: github.ref == 'refs/heads/develop'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: 构建Docker镜像
        run: |
          docker build -t inventory-backend:staging ./backend
          docker build -t inventory-frontend:staging ./frontend
          docker push registry.example.com/inventory-backend:staging
          docker push registry.example.com/inventory-frontend:staging

      - name: 部署到测试服务器
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.STAGING_HOST }}
          username: ${{ secrets.STAGING_USER }}
          key: ${{ secrets.STAGING_SSH_KEY }}
          script: |
            cd /opt/inventory-system
            docker-compose -f docker-compose.staging.yml pull
            docker-compose -f docker-compose.staging.yml up -d

      - name: 部署后冒烟测试
        run: |
          sleep 30
          curl -f https://staging.example.com/api/health || exit 1

      - name: 通知结果
        if: always()
        uses: 8398a7/action-slack@v3
        with:
          status: ${{ job.status }}
          text: '测试环境部署: ${{ job.status }}'
          webhook_url: ${{ secrets.SLACK_WEBHOOK }}

  # ═══════════ 部署到生产环境 ═══════════
  deploy-production:
    name: 部署生产环境
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production   # ← 需要人工审批

    steps:
      - uses: actions/checkout@v4

      - name: 生成版本号
        id: version
        run: echo "VERSION=$(date +%Y%m%d%H%M%S)-$(git rev-parse --short HEAD)" >> $GITHUB_OUTPUT

      - name: 构建镜像（带版本号）
        run: |
          VERSION=${{ steps.version.outputs.VERSION }}
          docker build -t inventory-backend:${VERSION} ./backend
          docker build -t inventory-frontend:${VERSION} ./frontend
          docker push registry.example.com/inventory-backend:${VERSION}
          docker push registry.example.com/inventory-frontend:${VERSION}

      - name: 数据库迁移
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.PROD_HOST }}
          username: ${{ secrets.PROD_USER }}
          key: ${{ secrets.PROD_SSH_KEY }}
          script: |
            cd /opt/inventory-system
            ./scripts/migrate.sh

      - name: 蓝绿部署
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.PROD_HOST }}
          username: ${{ secrets.PROD_USER }}
          key: ${{ secrets.PROD_SSH_KEY }}
          script: |
            VERSION=${{ steps.version.outputs.VERSION }}
            cd /opt/inventory-system

            # 保存当前版本用于回滚
            cp current-version.txt previous-version.txt

            # 拉取新版本
            docker pull registry.example.com/inventory-backend:${VERSION}
            docker pull registry.example.com/inventory-frontend:${VERSION}

            # 启动新容器
            docker-compose -f docker-compose.prod.yml up -d --no-deps backend frontend

            # 健康检查
            sleep 10
            curl -f http://localhost:8080/api/health || exit 1

            # 记录版本
            echo "${VERSION}" > current-version.txt

      - name: 生产冒烟测试
        run: |
          sleep 15
          curl -f https://www.example.com/api/health || exit 1

      - name: 打版本标签
        run: |
          VERSION=${{ steps.version.outputs.VERSION }}
          git tag -a "v${VERSION}" -m "Release ${VERSION}"
          git push origin "v${VERSION}"

      - name: 通知结果
        if: always()
        uses: 8398a7/action-slack@v3
        with:
          status: ${{ job.status }}
          text: '🚀 生产部署: ${{ job.status }} (${{ steps.version.outputs.VERSION }})'
          webhook_url: ${{ secrets.SLACK_WEBHOOK }}
```

## 11. 回滚机制与应急预案

### 11.1 回滚方式

| 方式 | 操作 | 耗时 |
|------|------|------|
| **Docker镜像回滚（推荐）** | 切回上一版本镜像 | ~30秒 |
| **Git回滚 + 重新部署** | `git revert` → 触发CI/CD | 5-10分钟 |
| **数据库回滚** | 执行降级迁移脚本 | 视情况 |

### 11.2 一键回滚脚本

```bash
#!/bin/bash
# scripts/rollback.sh
echo "========== 开始回滚 =========="
PREV_VERSION=$(cat /opt/inventory-system/previous-version.txt)
echo "回滚到版本: ${PREV_VERSION}"

cd /opt/inventory-system
export VERSION=${PREV_VERSION}
docker-compose -f docker-compose.prod.yml up -d --no-deps backend frontend

sleep 10
if curl -f http://localhost:8080/api/health; then
    echo "✅ 回滚成功"
else
    echo "❌ 回滚后健康检查失败，请人工介入！"
    exit 1
fi
echo "$(date) - 回滚到 ${PREV_VERSION}" >> rollback-history.log
echo "========== 回滚完成 =========="
```

### 11.3 回滚决策流程

```
上线后发现问题
    │
    ├── 严重（服务不可用、数据错误）→ 立即回滚 → 复盘
    ├── 一般（部分功能异常）→ 评估 → 影响大则回滚 / 影响小则hotfix
    └── 轻微（文案/样式）→ 常规修复，走正常CI/CD
```

## 12. 完整工作流程总览

### 12.1 日常开发全流程

```
① 开发阶段
   开发者创建feature分支 → 编写代码+测试 → 本地验证 → git push → 创建PR
       │
       ▼
② CI自动化阶段
   后端：格式检查→静态分析→单元测试→集成测试
   前端：类型检查→ESLint→组件测试→构建
   E2E：启动完整环境→端到端测试
   安全：依赖漏洞扫描
   任何一项失败 → ❌ 阻止合并
       │ 全部通过
       ▼
③ Code Review
   团队审查 → 批准/修改意见
       │ 通过
       ▼
④ 合并到develop → 自动部署测试环境 → 通知QA
       │
       ▼
⑤ QA验收
   功能验收 + 回归测试 → 发现问题退回 / 验收通过
       │ 通过
       ▼
⑥ 发布上线
   Release PR: develop→main → CI全量测试 → 审批
   → 合并 → 人工确认部署 → 自动构建→迁移→蓝绿部署→健康检查→打标签→通知
       │
       ▼
⑦ 上线后监控
   持续监控30分钟 → 异常则回滚/hotfix → 无异常则完成 ✅
```

### 12.2 紧急Bug修复流程（Hotfix）

```
线上紧急Bug → 从main创建hotfix分支 → 修复+补测试
→ CI测试 → 快速Review → 同时合并到main和develop
→ 自动部署 → 验证修复 → 持续监控
```

### 13.3 分阶段落地计划

```
Phase 1：基础CI（第1-2周）—— 最小可用
  ├── 搭建 GitHub Actions CI 流水线
  ├── 后端：单元测试框架 + 核心Service测试（~20个用例）
  ├── 前端：Jest配置 + 核心组件测试（~15个用例）
  ├── CI门禁：测试不通过不能合并PR
  └── 成果：每次提交自动运行测试，有问题立即发现

Phase 2：E2E测试（第3-4周）—— 保障核心流程
  ├── 搭建 Playwright 环境
  ├── 编写冒烟测试（登录 + CRUD + 上传，~10个用例）
  ├── CI中集成E2E测试
  └── 成果：核心用户流程有自动化保障，改一个地方不会把别的弄坏

Phase 3：自动化部署（第5-6周）—— 告别手动部署
  ├── Docker化前后端应用
  ├── 搭建测试环境，配置自动部署流水线
  ├── 配置生产环境蓝绿部署
  ├── 编写回滚脚本
  └── 成果：代码合并自动部署，回滚30秒完成

Phase 4：监控告警（第7-8周）—— 主动发现问题
  ├── 接入 Sentry 前端监控
  ├── 接入 UptimeRobot 健康检查
  ├── 配置飞书/钉钉告警通知
  ├── 配置 Loki + Grafana 日志系统
  └── 成果：线上Bug分钟级发现，告警自动推送

Phase 5：持续完善（持续进行）
  ├── 补充更多测试用例（提升覆盖率）
  ├── 性能基线测试
  ├── 定期安全扫描
  ├── 复盘总结优化流程
  └── 成果：自动化体系持续成熟
```

### 13.4 各阶段验证方法

| 阶段 | 验证方法 |
|------|---------|
| Phase 1 | 故意写一个会导致测试失败的代码提PR，确认CI报红、PR无法合并 |
| Phase 2 | 修改库存新增逻辑后，E2E自动发现编辑页面因此受影响 |
| Phase 3 | 代码合并到develop后，5分钟内测试环境自动更新；回滚脚本30秒恢复 |
| Phase 4 | 人为触发一个500错误，1分钟内飞书收到告警通知 |
| Phase 5 | 覆盖率稳步提升，线上故障次数逐月下降 |
