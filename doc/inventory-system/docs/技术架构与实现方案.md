### 1.2 架构说明（通俗版）

把整个系统想象成一个**餐厅**：

- **前端（Next.js）** = 餐厅的大堂和菜单。用户看到的所有页面、按钮、表格都在这里。它负责"好不好看、好不好用"。
- **后端（Golang + Gin）** = 餐厅的厨房。所有的数据处理、业务逻辑、安全检查都在这里完成。前端发出请求（点菜），后端处理后返回结果（上菜）。
- **数据库（MySQL）** = 餐厅的仓库/冰箱。所有的数据都存放在这里，需要的时候取出来，修改后放回去。
- **文件存储** = 餐厅的图片墙/资料柜。上传的图片和文件放在这里。

前端和后端之间通过 **HTTP 请求**（类似打电话下单）来通信，数据格式用 **JSON**（一种结构化的文本格式）。

## 2. 技术选型说明

### 2.1 后端：Golang + Gin

| 选择 | 原因 |
|------|------|
| **Golang** | 性能好、编译后是单个可执行文件（部署简单）、语法简洁、适合做API服务 |
| **Gin 框架** | Go语言最流行的Web框架，轻量、高性能、社区活跃、学习资料丰富 |
| **GORM** | Go语言最流行的ORM库（帮你用Go代码操作数据库，不用手写SQL） |
| **JWT** | JSON Web Token，业界标准的用户登录认证方案 |
| **Swagger** | 自动生成API文档，方便前端开发者查阅接口 |

### 2.2 前端：Next.js + TypeScript

| 选择 | 原因 |
|------|------|
| **Next.js** | React生态中最成熟的全栈框架，支持服务端渲染，对SEO友好 |
| **TypeScript** | JavaScript的增强版，编码时有类型检查，减少低级错误 |
| **TailwindCSS** | CSS工具库，快速编写样式而无需手写CSS文件 |
| **Ant Design** | 蚂蚁集团开源的企业级UI组件库，提供现成的表格、表单、弹窗等组件，非常适合管理系统 |
| **Axios** | 最流行的HTTP请求库，用于前端向后端发送请求 |

### 2.3 数据库：MySQL

| 选择 | 原因 |
|------|------|
| **MySQL** | 库存数据是结构化的（固定字段），MySQL擅长这类数据；支持事务保证数据一致性；最广泛使用的关系型数据库 |

### 2.4 其他工具

| 工具 | 用途 |
|------|------|
| **Docker** | 容器化部署，确保在任何环境下都能一致运行（可选） |
| **Nginx** | 反向代理，将前端和后端统一到一个域名下访问 |
| **Git** | 代码版本管理 |

## 3. 后端架构设计

### 3.1 分层架构

后端代码采用**经典三层架构**，每一层负责不同的职责：

```
请求进入 → Router(路由) → Middleware(中间件) → Controller(控制器) → Service(业务逻辑) → Repository(数据访问) → Database(数据库)
```

| 层 | 通俗解释 | 职责 |
|----|----------|------|
| **Router（路由层）** | 前台接待，根据你的请求指引你去哪个柜台 | 定义URL路径与处理函数的映射关系 |
| **Middleware（中间件层）** | 安检，每个请求必须先过安检 | 登录验证、权限检查、日志记录、参数校验 |
| **Controller（控制器层）** | 柜台工作人员，负责接收你的需求并返回结果 | 接收请求参数、调用Service、返回响应 |
| **Service（业务逻辑层）** | 后台处理人员，执行具体的业务规则 | 实现业务逻辑（校验、计算、组装数据） |
| **Repository（数据访问层）** | 仓库管理员，负责存取数据 | 数据库CRUD操作（增删改查） |
| **Model（模型层）** | 数据的定义/格式说明 | 定义数据结构（Go struct） |

### 3.2 中间件设计

```
每个API请求经过的中间件链：

请求 → [CORS] → [日志记录] → [JWT认证] → [权限校验] → [业务处理] → 响应
```

| 中间件 | 说明 |
|--------|------|
| **CORS** | 跨域资源共享，允许前端域名访问后端API |
| **Logger** | 记录每个请求的方法、路径、耗时、状态码 |
| **JWT Auth** | 从请求头提取Token，验证有效性，解析出用户信息 |
| **Permission** | 根据用户角色检查是否有权限访问当前接口 |
| **Recovery** | 捕获程序崩溃（panic），避免整个服务挂掉 |

### 3.3 统一响应格式

所有接口返回统一的 JSON 格式，前端可以用相同的逻辑处理：

```go
type Response struct {
    Code    int         `json:"code"`    // 0=成功，其他=错误码
    Message string      `json:"message"` // 提示信息
    Data    interface{} `json:"data"`    // 业务数据
}
```

### 3.4 配置管理

使用 YAML 配置文件管理所有可变参数：

```yaml

  port: 8080
```

## 4. 前端架构设计

### 4.1 项目结构思路

前端使用 Next.js 的 **App Router**（Next.js 13+ 的新路由系统），核心概念：

- **每个文件夹 = 一个页面路由**。比如 `app/inventory/page.tsx` 对应 URL `/inventory`
- **组件化开发**。把页面拆成一个个可复用的小模块（组件）
- **前后台分离**。前台页面和后台管理页面使用不同的布局

### 4.2 状态管理

| 方案 | 用途 |
|------|------|
| **React Context** | 全局状态：用户登录信息、权限、主题 |
| **React Query (TanStack Query)** | 服务端数据：库存列表、详情等从后端获取的数据，自动缓存和刷新 |
| **useState/useReducer** | 局部状态：表单输入、弹窗开关等页面内部状态 |

### 4.3 通俗解释

- **React Query** 的作用：你在库存列表页查看数据，跳转到详情页再回来，数据还在不需要重新加载。它帮你管理"从后端拿来的数据"的缓存和刷新。
- **Ant Design** 的作用：提供现成的表格（Table）、表单（Form）、按钮（Button）、弹窗（Modal）等，不需要从零开始写这些复杂的UI组件。
- **Axios** 的作用：封装成统一的请求工具，自动带上登录Token、统一处理错误。

### 4.4 页面路由设计

```
/                           → 重定向到 /login 或 /inventory
/login                      → 登录页

# 前台页面
/inventory                  → 库存列表页
/inventory/[id]             → 库存详情页

# 后台管理页面
/admin                      → 重定向到 /admin/dashboard
/admin/dashboard            → 仪表盘
/admin/inventory            → 库存管理列表
/admin/inventory/create     → 新增库存
/admin/inventory/[id]/edit  → 编辑库存
/admin/inventory/deleted    → 已删除数据
/admin/attachments          → 附件管理
/admin/users                → 用户管理
/admin/users/roles          → 角色管理
/admin/logs/operations      → 操作日志
/admin/logs/changes         → 变更日志
/admin/settings             → 系统配置
```

## 5. 数据库设计思路

### 5.1 为什么选 MySQL

| 考虑因素 | MySQL优势 |
|----------|----------|
| 数据结构 | 库存数据字段固定，非常适合关系型数据库的表结构 |
| 事务支持 | 修改库存数量时需要事务保证数据一致性（不会出现数据错乱） |
| 查询能力 | 支持复杂筛选：模糊搜索、范围查询、多条件组合 |
| 成熟度 | 全球使用最广泛的开源数据库，文档和教程非常丰富 |

### 5.2 索引设计思路

**索引的通俗解释**：索引就像一本书的目录。没有目录时找一个章节需要一页页翻；有了目录可以直接翻到对应页码。数据库索引同理，能大幅加快查询速度。

| 表 | 索引字段 | 原因 |
|----|----------|------|
| inventories | `material_code` | 编码唯一性校验和精确查询 |
| inventories | `category` | 按分类筛选 |
| inventories | `status` | 按状态筛选 |
| inventories | `created_at` | 按时间排序 |
| attachments | `inventory_id` | 按库存ID查找附件 |
| operation_logs | `created_at` | 按时间范围查询日志 |
| change_logs | `inventory_id` | 按库存记录查变更历史 |

### 5.3 软删除机制

**通俗解释**：删除数据时不是真的从数据库移除，而是给它打一个"已删除"的标记。就像你把文件放进回收站而不是彻底删除，需要的时候还能恢复。

```
删除前: is_deleted = 0 (正常显示)
删除后: is_deleted = 1 (列表中隐藏，但数据还在)
恢复:   is_deleted = 0 (重新显示)
```

查询时自动加条件 `WHERE is_deleted = 0`，只显示"正常"的数据。

### 5.4 乐观锁机制

**通俗解释**：防止两个人同时编辑同一条数据导致其中一个人的修改被覆盖。

```
场景：张三和李四同时打开了编码为 YL-001 的库存编辑页面
1. 张三看到的 version = 1，李四看到的 version = 1
2. 张三先保存，数据库执行: UPDATE ... WHERE version = 1 → 成功，version变为2
3. 李四后保存，数据库执行: UPDATE ... WHERE version = 1 → 失败（因为version已经是2了）
4. 系统提示李四："数据已被其他人修改，请刷新后重新编辑"
```

## 6. 核心功能实现思路

### 6.1 用户登录认证（JWT）

**通俗解释**：JWT就像一张"通行证"。登录成功后服务器发给你一张通行证（Token），之后每次访问都出示这张通行证，服务器验证通行证有效就放行。

```
1. 用户提交用户名+密码
2. 后端验证密码（用 bcrypt 对比加密后的密码）
3. 验证通过，生成JWT Token（包含用户ID、角色、过期时间）
4. 返回Token给前端
5. 前端保存Token到浏览器（localStorage）
6. 之后每次请求在Header中携带: Authorization: Bearer <token>
7. 后端中间件解析Token，提取用户信息，注入到请求上下文中
```

### 6.2 权限控制实现

```
路由定义时指定所需角色：
  POST /api/v1/inventories  → 需要角色: admin, operator
  DELETE /api/v1/inventories/:id → 需要角色: admin (或可配置的operator)

中间件处理流程：
  1. 从JWT中提取用户角色
  2. 对比当前接口要求的角色列表
  3. 匹配 → 放行
  4. 不匹配 → 返回 403 权限不足
```

### 6.3 文件上传实现

```
前端：
  1. 用户选择文件 / 拖拽文件
  2. 前端校验文件格式和大小（快速反馈）
  3. 使用 multipart/form-data 格式上传到后端
  4. 显示上传进度条

后端：
  1. 接收文件流
  2. 校验文件后缀 + MIME类型（双重安全检查）
  3. 校验文件大小
  4. 生成UUID文件名，按规则创建存储路径: uploads/202602/{库存ID}/{uuid}.jpg
  5. 保存文件到磁盘
  6. 如果是图片，生成缩略图
  7. 在数据库 attachments 表中记录文件元信息
  8. 返回上传结果
```

### 6.4 库存预警实现

```
方式1 — 查询时计算（推荐，简单）：
  查询库存列表时，后端对比 quantity 和 safety_stock
  如果 quantity < safety_stock，在返回数据中标记 warning: true
  前端根据 warning 字段高亮显示

方式2 — 定时任务（可选，后期优化）：
  定时扫描所有库存，发现预警记录后发送通知（邮件/消息）
```

### 6.5 数据导出实现

```
1. 前端点击"导出"按钮，传递当前筛选条件
2. 后端根据筛选条件查询数据（不分页，取全量）
3. 使用 excelize 库（Go语言Excel处理库）生成 .xlsx 文件
4. 将文件作为HTTP响应返回，设置Content-Type为下载类型
5. 前端浏览器自动弹出下载
```

### 6.6 变更日志实现

```
编辑保存时：
  1. 从数据库读取当前记录的旧值
  2. 对比每个字段的新值和旧值
  3. 不同的字段写入 change_logs 表
  4. 记录: 字段名、旧值、新值、操作人、时间

示例：
  修改前: quantity=100, location="A区-01"
  修改后: quantity=80,  location="A区-02"
  
  写入2条变更记录:
    - field=quantity, old=100, new=80
    - field=location, old=A区-01, new=A区-02
```

## 7. 部署方案

### 7.1 开发环境

```
本地电脑运行：
  - 后端: go run main.go       → http://localhost:8080
  - 前端: npm run dev           → http://localhost:3000
  - 数据库: 本地安装 MySQL       → localhost:3306
  - 前端请求后端: 通过 Next.js proxy 或直接跨域
```


### 7.3 Docker 部署（可选，推荐）

使用 Docker Compose 一键启动所有服务：

```yaml
# docker-compose.yml 概念说明
services:
  mysql:      # 数据库服务
  backend:    # Go后端服务
  frontend:   # Next.js前端服务
  nginx:      # 反向代理
```

好处：不管你的服务器是什么系统，只要装了 Docker，一条命令 `docker-compose up` 就能把整个系统跑起来。

## 9. 开发流程建议

### 9.1 推荐开发顺序

作为无编程经验的开发者，建议按以下顺序逐步实现，每一步都是在前一步的基础上增加功能：

```
阶段1: 基础骨架（1-2周）
  ├── 搭建后端项目框架（路由、中间件、配置）
  ├── 搭建前端项目框架（页面路由、布局、组件库引入）
  ├── 创建数据库和表结构
  └── 实现用户登录/登出

阶段2: 核心CRUD（2-3周）
  ├── 后端：库存增删改查 API
  ├── 前端：库存列表页（分页、筛选）
  ├── 前端：库存新增/编辑表单
  ├── 前端：库存详情页
  └── 前端：库存删除（软删除）

阶段3: 附件功能（1-2周）
  ├── 后端：文件上传/下载 API
  ├── 前端：文件上传组件（拖拽、进度条）
  ├── 前端：图片预览（缩略图+大图）
  └── 前端：文件列表与下载

阶段4: 权限与管理（1-2周）
  ├── 后端：角色权限中间件
  ├── 后台：用户管理页面
  ├── 后台：角色管理
  └── 前后台权限边界

阶段5: 日志与增强（1周）
  ├── 变更日志记录与查询
  ├── 操作日志记录与查询
  ├── 数据导出功能
  └── 仪表盘

阶段6: 优化与部署（1周）
  ├── 性能优化
  ├── 安全加固
  ├── 部署配置
  └── 测试与验收
```
